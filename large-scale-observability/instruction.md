# Large-Scale Observability for Ride-Hailing Fleet — Multi-Turn Task (Hardened v5, NOT API log analysis)

This is a multi-turn terminal-bench task with 2 steps, now significantly hardened and explicitly NOT a generic API access log analyzer (no JSON log file parsing, no request-counts/error-rates/latency-percentiles/unique-users aggregation). You are building a ride-hailing fleet observability SDK in Go for a high-throughput dispatch platform handling 10k+ req/sec, tracking riderID -> driverID matching, pickup/dropoff lat/lng geohash, trip lifecycle requested/matched/started/completed, driver heartbeat presence, ETA calculation, surge pricing, fleet dispatch optimization, fare aggregation.

## Overall Goal
Implement package `observability` in module `ride-observability` that provides:
- Distributed tracing with `TraceContext` (TripID 32 hex, SegmentID 16 hex) propagation via custom single-header `x-ride-trace` = tid:sid:pid:1/0 (4 colon parts even when pid empty as tid:sid::1), with strict Flags 1/0, ParentID chain consistency across root->child->grandchild, nil ctx handling, defensive copies, duplicate-key last-wins, distinct counting 128 limit, all-zero IDs invalid for propagation, Flags normalized in ContextWithTrace
- Ride metrics (Counter for ride_requests_total, Gauge for active_rides, Histogram for ride_duration_seconds/ETA) with thread-safety, defensive copies for WithLabels map and WithBuckets slice (mutating original after creation must not affect), label value truncate 256 before cardinality key and reuse after truncation (collision reuse), sorted keys order irrelevant, Gauge Set/Add ignore NaN/Inf, Counter Add >=0 ignore negative/NaN/Inf, Histogram default buckets 11 cumulative inclusive sorted ascending with dedup of duplicate upper bounds and NaN/Inf filtering, deep copy Collect including Buckets, provider isolation, type conflict first wins, description first wins, and cardinality limiting in step2 per-name drop/aggregate with __overflow__
- Structured JSON logging correlated with tracing for trip events (ride requested, driver matched, trip started/completed, surge triggered), atomic per-line writes, shared mutex across With chain for 100 concurrent goroutines producing 100 valid JSON lines no interleaving, immutable With, level filtering debug<info<warn<error> default info case-insensitive, WithOutput nil fallback stderr, service field cannot be overridden, field duplicate last-wins, timestamp RFC3339Nano UTC recent, concurrent exact lines counting

## References and Prior Art (GitHub Links — for novelty context)

This task's prior version was a near-verbatim clone of OpenTelemetry Go SDK, which models could solve by recall. The hardened version intentionally inverts semantics to punish recall:

- OpenTelemetry Go SDK (original clone source): https://github.com/open-telemetry/opentelemetry-go
- OpenTelemetry Go Contrib (propagation helpers): https://github.com/open-telemetry/opentelemetry-go-contrib
- W3C Trace Context spec (contrast with our custom single-header x-ride-trace): https://github.com/w3c/trace-context
- Go standard library context (used for ContextWithTrace): https://github.com/golang/go/tree/master/src/context
- Prometheus client model (metrics naming inspiration, but our regex is stricter): https://github.com/prometheus/client_model

Our custom propagation `x-ride-trace: traceID:spanID:parentID:sampled` intentionally differs from W3C `traceparent: 00-traceID-spanID-flags` and from OTel's four-header legacy. RatioSampler uses last 8 hex chars uint32/2^32 vs OTel's first 16 hex uint64/2^64. See `steps/1_step_one/instruction.md` for exact spec.
